# セキュリティ再点検（2026年10月28日）

学習塾の生徒・講師管理を、SQLインジェクション、XSS、アクセス制御、設定と暗号化、依存関係、DoS/DDoSの6項目で再点検する。対象ソースは開始時点で30e8b55。共有環境はPHP 8.2.12、Apache 2.4.58、MariaDB 10.4.32だった。

実DBへの送信試験や大量アクセスは行わない。別ポートの専用PHP・MariaDBと架空データを使い、少数の直列リクエストで境界を確認する。共有PHP・Apacheの切替と再起動、DB本体の変更は今回も実施しない。

## 追加対策の設計

以下の5項目はすべて実装済みで、`C:\xampp\htdocs\βteam`へ反映している。アプリの修正はb430a1a、依存関係の検証は93de614、診断記録は3a94572としてGitHubへpush済み。根拠・影響の欄は修正前の状態を示す。環境側の残件はこの表とは分けて扱う。

| ID | 重要度 | 修正前の根拠・影響 | 採用した対策 | 実装状況・実装先 |
|---|---|---|---|---|
| DOS-01 | 中 | login.phpでIP制限の結果にかかわらずメール別bucketも作成する。制限後も異なるメールを送り続けるとrate_limitsが増える | IPで拒否したらメール別処理を呼ばず429を返す。Retry-Afterを維持 | 実装・反映済み：[login.php](../login.php) |
| DOS-02 | 中 | students.php・teachers.phpの部分一致検索に実行回数制限がない | 講師IDごとに両一覧共通30回/60秒。31回目は429。検索語をbucketキーに含めない | 実装・反映済み：[共通制限](../functions.php)、[生徒一覧](../students.php)、[講師一覧](../teachers.php) |

DBの制限は接続ごとの設定に限り、共有サーバーのグローバル変数やスキーマを変更しない。クエリ時間はDB側の検査タイミングに依存し、厳密な全処理の終了時刻を保証しない。MySQLのmax_execution_timeは読み取りSELECTが対象。書き込み・COMMITや回線へのDDoSをこの設定だけで防いだとは扱わない。

この設計を先に保存し、その後に下記の実装と検証を行った。

リソース試験の初回は保守用データの準備SQLにMariaDB1093が発生した。対象表をVALUES内で参照する試験コードを修正し、架空データを復元してから再実行した。本体の保守処理を失敗扱いから外すために試験を削除したものではない。初回失敗と最終結果を両方保存している。

結果はローカルのoutput/security-20261028、output/security-runtime.json、output/apache-security.jsonに保存する。再実行方法は[セキュリティ検証手順](セキュリティ検証手順.md)。実DBの書き換え、外部メール送信、実アプリへの攻撃・負荷試験は行っていない。

## 判断と未確認範囲

SQLi・XSS・アクセス制御の点検では、確認した経路に新たな未修正問題を再現しなかった。ただし全経路・すべての攻撃手法に対して無欠陥であることを保証するものではない。XSSはHTTP出力のエスケープとDOMの静的確認を根拠にし、CSPだけを防御根拠としていない。

差分を自己レビューし、DoSの処理順・制限・保守と、Windowsの改行変換による整合性検証の問題を受け入れて修正した。今回のアプリ差分に未修正の必須指摘は残っていない。次の環境側の要更新事項を解決済みとして扱わない。

MySQL 8.0本体での時間制限、通信破棄時の接続タイムアウト実測、実際の大規模負荷、上流の遮断、実SMTP・本番HTTPSの受信確認は未実施。DB時間制限は負荷時の全リクエストを3秒以内へ収める保証ではない。

## 環境側の残件

- PHP 8.2.12は重大な既知問題の修正前。アプリ実行前に到達する経路があり、アプリ改修だけでは解消しない。Windowsでは8.2.35の表示だけで判断せず、2026-10-26のBrotli修正を含む再ビルド配布物も確認する。
- Apache 2.4.58はWindows向けSSRF等の修正前。実際の攻撃成立には設定条件の確認も必要。Apacheを更新する手順は別に用意する。
- MariaDB 10.4はサポート終了済み。既存DBをバックアップ・別環境で復元してから、サポート中系列へ移行する計画が必要。
- localhostのHTTPは開発用。公開時はHTTPS、アプリ専用DBアカウント、接続元制限を適用する。CookieのSecureをlocalhostのHTTPへ強制しない。
- 大規模DDoSは上流の通信遮断・WAF・接続数制限等が必要。今回、実回線での負荷試験は行わない。

公開運用までに管理者が実施する作業は[サーバー運用強化手順](サーバー運用強化手順.md)にまとめた。実測ではDB接続はroot・空パスワードのまま、Apacheのmod_reqtimeoutは未ロードだった。実際の接続情報の値をログ・Gitへ保存したり、今回これらの設定を自動変更したりしていない。
