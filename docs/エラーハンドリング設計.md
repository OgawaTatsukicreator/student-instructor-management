# エラーハンドリング設計

2026年10月22日。対象はβteamの全PHP画面、認証、保存・削除、メール認証、初期管理者CLI。実装前に既存経路を棚卸しし、以下の契約を採用する。

## 応答の契約

| 状況 | HTTP | 表示・処理 |
|---|---:|---|
| 未ログイン、期限切れ、認証情報失効 | 303 | 更新せずログインへ。失効理由を短く表示 |
| 保存成功 | 303 | 保存先または一覧へ移動し完了表示。POSTを再送しない |
| 不正なID・ページ・version・操作名 | 400 | 保存せず、安全なGETの画面へ戻る |
| 権限不足・担当解除・CSRF不一致 | 403 | 更新しない。CSRF失敗時はフォームを開き直す導線 |
| 存在しない対象、operatorがadmin詳細を指定 | 404 | 一覧への導線。権限外の講師の存在を明かさない |
| 許可しないHTTPメソッド | 405 | Allowを返し、更新しない |
| 他者更新・削除・業務制約との競合 | 409 | 自動上書きしない。未保存入力を保持し、最新画面を開く導線 |
| 64KiB超のPOST、入力項目数超過 | 413 | PHPが入力を切り捨てた状態で保存しない |
| 対応外のPOST形式 | 415 | URLエンコード・multipart以外を受理しない |
| 必須・形式・文字数・文字コード・重複メール・認証不一致 | 422 | 項目と要約へ表示。入力は保持し、パスワード・認証コードは再表示しない |
| ログイン・再認証・メール送信の回数上限 | 429 | Retry-Afterと待機案内。別セッションでも回数を共有 |
| 設定不整合・SQLの不具合・予期しない例外 | 500 | 内部詳細を伏せ、問い合わせIDを表示 |
| DB接続不能・ロック待ち・SMTP・セッション保存障害 | 503 | Retry-Afterと復旧案内。自動でPOSTを再送しない |

表示と状態コードを一致させる。非標準の419は使用しない。DBへの到達前にメソッド・入力容量を検証する。画面表示はGET/HEAD、フォームはGET/HEAD/POST、削除とログアウトはPOSTのみ。パスワード変更でメール認証を無効にした設定は引き続き使用できる。

## 共通処理

1. 設定読込より前に例外・警告・致命的エラーの処理を設置する。HTTP出力はバッファにため、途中描画の失敗でも未完成HTMLを捨てて一枚のエラー画面にする。
2. 想定内の業務エラーは公開可能な文言、HTTP状態、項目名、待機秒数を持つ。DB例外の生メッセージを業務エラーへコピーしない。
3. 一時DB障害だけを503へ分類し、テーブル不足・不正SQL等は500にする。保存トランザクションは例外時にROLLBACKする。ROLLBACK自身の失敗は元の障害を隠さず記録する。
4. エラー画面を作る処理はDB・現在ユーザーの取得に依存させない。出力自身に失敗しても安全な最小HTMLへ戻せるようにする。
5. 500/503では処理結果を断定しない。「処理結果を確認してからやり直す」と案内する。DB確定後のセッション障害など、保存済みの可能性があるため。
6. 安全なGETリンクだけを表示する。Refererや外部URLをそのまま戻り先にせず、固定画面と数値IDの許可リストを使う。

## 認証とログアウト

- ログイン失敗の文言・HTTPはメール存在の有無で変えない。既存のIP単位・アカウント単位の制限を維持し、429へ統一する。
- 現在のパスワードの確認も講師ID単位で15分5回に制限する。正しく照合したらその再認証カウンターを解除する。
- 無操作30分に加え、連続利用でもログインから8時間で再認証する。パスワード変更で絶対期限を延ばさない。
- セッション開始・ID変更・保存失敗を確認し、成功したように処理を続けない。CookieのHttpOnly・SameSite=LaxとHTTPS時のSecure、CSRF検証は維持する。
- ログアウトでは先に認証情報を消去してセッションを更新する。メール認証のDB後始末が失敗しても、ログアウト済み状態は維持する。

## 入力と保存

氏名はUTF-8で各1〜50文字。特記事項はUTF-8で2,000文字以内、改行・タブを許可し、NUL等の制御文字は拒否する。生年月日は1000年以降、今日以前の実在する日付。配列入力を文字列とみなさず、IDとversionの上限も確認する。

generalから届いた許可外の項目は保存しない。担当・権限・credential_versionを保存トランザクション内でも確認する。競合時は古いversionのまま再送して強制上書きしない。

## SMTPと認証保留

設定不足と送信失敗は503。送信失敗時は保留トークンをセッションから先に消し、DB後始末は別に保護する。未送信の行は認証に使用できない。送信回数制限は429。コード不一致は422と残り回数、期限切れ・5回失敗は手続きを終了して入力開始へ戻す。

## ログ

問い合わせID、UTC日時、イベント、HTTP状態、固定ルート名、例外クラス、数値コード、ソースのファイル名と行番号をJSONで記録する。生の例外文、SQL・パラメーター、POST本文、メール、Cookie、セッションID、パスワード、OTPは記録しない。

主な保存先はGit・Web管理外のruntime/application.log。書けない場合はPHP/SAPIログへ安全な情報だけを出す。ログ失敗で例外処理を再帰させない。ログの保管期間と削除はチームの運用で定める。

## 表示の判断基準

SHIG [55「エラー表示は建設的にする」](https://www.sociomedia.co.jp/9535)により、失敗理由と次の操作を示す。[66「操作の近くでフィードバックする」](https://www.sociomedia.co.jp/9729)により、入力欄近くのエラーと要約を維持する。要約へフォーカスを移し、競合時には最新画面へのリンクを示す。秘密の入力は保持しない。

## 検証方針

専用の一時DB・別ポートPHP・外部へ配送しないSMTPで実施する。権限外更新、CSRF横断、メソッド、SQLインジェクション、XSS、型崩し、不正UTF-8、セッション固定化・失効、現パスワード試行制限を検証する。DB接続不能、SQL不具合、ロック待ち、設定不正、セッション保存失敗、ログ失敗、SMTP失敗を注入し、HTTP分類・更新の有無・秘密情報非露出・復旧導線を確認する。
