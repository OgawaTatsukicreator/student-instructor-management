# サーバー運用強化手順

2026年10月28日の再点検で確認した環境側の残件と、後日管理者が行う作業。今回は共有サービス・DB・認証情報を変更していない。アプリを修正したことを、基盤の更新や大規模DDoSへの対策完了とは扱わない。

## 確認した状態

| 対象 | 読み取りで確認した内容 | 対応 |
|---|---|---|
| PHP | 8.2.12 | [PHP更新手順](PHP更新手順.md)。更新前の重大な既知問題が残る |
| Apache | 2.4.58、Windows MPM、headers/rewrite/ssl有効、reqtimeout未ロード | 修正版への移行と、受信時間制限の導入 |
| MariaDB | 10.4.32。10.4系列は2024-06-18に保守終了 | サポート中系列の別環境へ復元して移行検証 |
| DB接続 | rootかつ空パスワードであることを値を出さず確認 | [DB接続権限](DB接続権限.md)に従い専用アカウントへ変更 |
| Apacheの待機 | Timeout=300、KeepAlive=On、KeepAliveTimeout=5、MaxKeepAliveRequests=100 | 共有する他アプリへの影響を確認し、必要な待機時間と接続数を決める |
| 利用URL | localhost:8080のHTTPを開発用に使用 | 公開・LAN運用ではHTTPSと接続元制限を構成 |

Apacheの既知問題は[公式脆弱性一覧](https://httpd.apache.org/security/vulnerabilities_24.html)で影響版と成立条件を照合する。2.4.58はWindows UNCアクセスを伴うSSRF等の修正前だが、特定CVEの実攻撃成立を再現したという意味ではない。[公式配布情報](https://httpd.apache.org/download.cgi)と、利用するWindows向け配布元の互換性・署名・ハッシュを確認する。

MariaDBの系列選択は[公式保守期間](https://mariadb.org/about/#maintenance-policy)を確認する。2026-10-28時点では10.11と11.4が保守中の候補。DB移行に必要な検証を省略して、そのまま既存のデータディレクトリへ新しいバイナリを上書きしない。

## 更新と切り戻し

1. 稼働中の全XAMPPプロジェクト、PHP拡張、Apacheモジュール、DB利用者、ポートと設定ファイルを記録する。
2. DBを整合性のある方法でエクスポートし、htdocs外にソース・設定と分けて保管する。専用環境で復元し、文字コード・外部キー・データ件数・アプリ操作を確認する。
3. 修正済みPHP・Apacheと保守中のDBを、別フォルダー・別ポートで構成する。DLLの互換性を確認する。PHPだけの置換でApacheやDBも更新済みとはみなさない。
4. 専用DBユーザーへ必要なテーブル権限だけを付け、実データを含まない環境でログイン・全権限・CRUD・パスワード変更・メール・保守処理を試す。
5. 他プロジェクトにも影響する停止時間と切り替え範囲を決める。Apache構文検査後、更新を行う作業で共有サービスを切り替える。今回の診断では実行しない。
6. 切替直後にWeb経由のPHP・Apache・OpenSSL等の実際の版を確認し、アプリと他プロジェクトを確認する。公開したphpinfoや一時プローブを残さない。
7. 切り戻す場合は旧環境・接続設定・バックアップを使う。更新後に書かれたデータの扱いを先に決め、単純な旧DB上書きで更新データを失わないようにする。

## 通信・接続の制限

回線を埋めるDDoS、TCP接続枯渇、PHP実行前の低速送信は、検索の429やDB時間制限では防げない。公開経路の前段で接続数・リクエスト数を制限し、必要に応じてWAF/CDN・回線事業者の遮断を利用する。前段を設けた場合はオリジンサーバーへ直接到達する経路も制限する。サービスやDNSを今回新規契約・変更する作業は行っていない。

Apache側では、管理者がmod_reqtimeoutの有効化と受信時間を検討する。次は検討用の例で、共有設定へ自動適用するものではない。対象vhostの通信条件を確認し、遅い正規利用者が拒否されないか別環境で試す。LoadModuleは二重登録を避けてサーバー設定、その他はサーバー設定またはvhostに置く。.htaccessへ記載しない。

```apache
LoadModule reqtimeout_module modules/mod_reqtimeout.so
RequestReadTimeout handshake=10 header=20-40,MinRate=500 body=20,MinRate=500
Timeout 60
KeepAlive On
KeepAliveTimeout 5
MaxKeepAliveRequests 100
LimitRequestFields 40
LimitRequestFieldSize 8190
LimitRequestLine 4096
```

mod_reqtimeoutが存在しない場合に制限を黙って省略せず、モジュールを用意して構文検査する。Windows MPMの同時処理数はサーバー容量・正規の同時利用数と合わせて決める。ServerTokens/ServerSignature等による情報表示の抑制は、脆弱性を修正する更新の代わりにはならない。

LANから使わない開発環境ではloopback限定の待受とファイアウォール制限を検討する。公開時は正しい証明書でHTTPSを構成し、HTTPで認証フォームを配信・送信しない。プロキシを置く場合は信頼する中継元だけに限定し、アプリが任意のX-Forwarded-For/Protoを信じる構成に変更しない。

根拠：[Apache mod_reqtimeout](https://httpd.apache.org/docs/2.4/mod/mod_reqtimeout.html)、[Apacheリクエスト上限](https://httpd.apache.org/docs/2.4/mod/core.html#limitrequestfields)、[OWASP DoS対策](https://cheatsheetseries.owasp.org/cheatsheets/Denial_of_Service_Cheat_Sheet.html)。

## 制限レコードの保守

管理者は1日1回を目安に、プロジェクト直下でまず対象件数を確認する。以下の--pruneはデータを削除する操作なので、接続先設定とバックアップを確認して実行する。Webからは実行できない。

```powershell
C:\xampp\php\php.exe maintenance.php
C:\xampp\php\php.exe maintenance.php --prune
```

既定は件数確認のみ。--pruneは開始時点で24時間より古いrate_limitsと、期限切れpassword_changesを各最大1000行削除する。講師・生徒・担当関係は削除しない。有効期限内の制限・メール認証行を保持する。1回の処理で対象が残る場合は、間隔をおいて確認と削除を繰り返す。無制限ループで一括処理しない。

既存DDLにはwindow_startedとexpires_atの索引がある。チーム側で定義を変更している場合は[DB設計](DB設計.md)と照合し、索引・必要な権限を確認する。今回、実用DBに対して保守CLIを実行したり、スキーマを変更したりしていない。
